# GarmentOS Cloud — سجل القرارات المعمارية (Architecture Decision Records - ADR)

## ADR-001: هيكل المستودع المشترك (Monorepo Architecture)
- **القرار:** استخدام Monorepo منظم يضم:
  - `apps/api`: واجهة برمجة التطبيقات الخلفية والمنطق التشغيلي (Laravel 13.x REST API / `laravel/framework: ^13.17`).
  - `apps/web`: لوحة الإدارة المتكاملة للمصنع والمنصة (React 19 + TypeScript + Vite + Tailwind CSS).
  - `apps/storefront`: واجهة المتجر الإلكتروني المخصصة للمستهلكين لكل مصنع.
  - `packages/ui`: مكتبة مكونات التصميم المشتركة والـ Tokens.
- **السبب:** سهولة مزامنة الأنواع (Types)، تبسيط النشر والاختبارات، ومشاركة مكونات التصميم دون تشتيت الكود في مستودعات منفصلة.

## ADR-002: استراتيجية العزل المتعدد للمستأجرين (Multi-Tenancy Strategy)
- **القرار:** قاعدة بيانات موحدة مشتركة (Shared Database with Shared Schema) مع حقل إلزامي `tenant_id` لكل جدول يخص الشركات.
- **التنفيذ الصارم:**
  - تفعيل Global Query Scopes في الباك إند لمنع أي استعلام من الوصول لسجلات شركة أخرى تلقائيًا.
  - دعم Row-Level Security (RLS) في PostgreSQL لطبقة حماية إضافية على مستوى المحرك.
  - استخراج هوية الشركة (Tenant Context) من التوكن المعتمد (JWT / Sanctum Session) وليس من مدخلات العميل.
  - عزل مجلدات التخزين، الكاش (Cache Key Prefixing: `tenant:{id}:*`) وقوائم انتظار المهام.

## ADR-003: دقة الحسابات النقدية والمخزنية (Money & Decimal Quantities)
- **القرار:**
  - المبالغ المالية: تخزن بنوع `DECIMAL(14, 4)` في قاعدة البيانات ولا يتم استخدام `FLOAT` أو `DOUBLE` نهائيًا لمنع أخطاء التقريب المالي.
  - كميات الأقمشة والخامات: تخزن بنوع `DECIMAL(12, 4)` لدعم الكسور الدقيقة في الأمتار والكيلوجرامات وقطع الهالك.
  - كل حركة مالية أو مخزنية تصدر بوحدة قياس وعملة صريحة.

## ADR-004: إدارة حركات المخزون (Double-Entry Ledger Style Inventory)
- **القرار:** يمنع تعديل رصيد المخزون مباشرة في جدول الأصناف (`inventory_items.quantity = quantity + 10`).
- **السبب:** يجب أن يكون الرصيد ناتجًا تراكميًا أو مجمعًا من جدول حركات المخزون (`inventory_transactions`)، مع تسجيل:
  - نوع الحركة (استلام، صرف، تحويل، فاقد قص، تسوية جرد).
  - المستند المرجعي (أمر شراء، أمر إنتاج، محضر جرد).
  - المستخدم المسؤول وتاريخ ووقت العملية.

## ADR-005: فصل خامات العملاء في خدمات القص والتصنيع للغير (Customer-Supplied Materials)
- **القرار:** فصل سجلات خامات العملاء عن مخزون خامات المصنع المملوكة له في الجداول والتقارير المالية.
- **السبب:** خامات العميل لا تعتبر أصلًا من أصول الشركة ولا تدخل في تقييم المخزون المالي للمصنع ولا في تكلفة البضاعة المباعة، بل تسجل كأمانات تشغيل تحت عهدة المصنع بحسابات مستقلة.

## ADR-006: التوجيه الحتمي للمتاجر وإدارة النطاقات (Deterministic Storefront Tenant Routing & Domain Security)
- **القرار:** إزالة أي سلوك افتراضي غير آمن لاختيار أول مستأجر نشط (`Tenant::where('status', 'active')->first()`) نهائياً من مسارات المتاجر العامة.
- **التنفيذ الصارم:**
  - حل النطاق حتمياً عبر `DomainResolutionService` عبر النطاق الفرعي (`subdomain.{base_domain}`) أو النطاق المخصص الموثق (`custom_domain`) أو المعرف المعتمد للمتجر.
  - رفض الطلبات غير المعروفة أو المعلقة أو غير الموثقة برموز استجابة آمنة وصريحة (404 / 403).
  - عدم الوثوق بترويسة `X-Tenant-ID` المقدمة من المتصفح في المسارات العامة لمنع انتحال صفة المستأجرين.
  - اشتراط التحقق من سجلات DNS (TXT Verification Token) قبل تفعيل أي نطاق مخصص.
  - توثيق كافة التعديلات الإدارية على النطاقات في سجل الرقابة والتدقيق العام (`audit_logs`).

## ADR-007: توافقية أنواع المفاتيح الأجنبية مع PostgreSQL (PostgreSQL Canonical Foreign Key Alignment)
- **القرار:** استخدام نوع `unsignedBigInteger` لجميع العلاقات التي تشير إلى جدول `users.id` (الذي يستخدم المعرف الرقمي `bigint unsigned`).
- **السبب:** قواعد بيانات PostgreSQL تفرض تطابقاً صارماً بين نوع المفتاح الأساسي والمفتاح الأجنبي؛ ربط `UUID` مع `BIGINT` يسبب فشل الهجرة DDL Fatal Error. تم تصحيح جدول `pos_sessions.user_id` ليطابق النموذج القياسي المعتمد في المنصة.

## ADR-008: الحساب الإلزامي والموثوق للأسعار وتكاليف الشحن سيرفر-سايد (Authoritative Server-Side Pricing & Shipping Policy)
- **القرار:** حظر الوثوق التام بأي أسعار أو مسميات أو أكواد أو تكاليف شحن مرسلة من متصفح العميل في أوامر الشراء للمتجر الإلكتروني.
- **التنفيذ الصارم:**
  - استخراج الأسعار وأكواد الـ SKU وأسماء المنتجات حصرياً من سجلات قاعدة البيانات الموثوقة للمستأجر الحالي.
  - احتساب تكاليف الشحن عبر سياسة سيرفر-سايد محددة جغرافياً وقيمياً (`calculateAuthoritativeShipping`).
  - تطبيق المعاملات البنكية الذرية (`DB::transaction`) وقفل السجلات للتزامن (`lockForUpdate`) لمنع البيع الزائد (Overselling).

## ADR-009: توحيد الهوية البصرية والباليتة الرسمية المعتمدة (Approved Brand Identity System)
- **القرار:** الالتزام الصارم بالباليتة الرسمية المعتمدة للمنصة:
  - اللون الأساسي (Primary): `#460809` (Imperial Burgundy).
  - اللون الثانوي (Secondary): `#000000` (Obsidian Black).
  - اللون الثالث (Tertiary): `#FFFFFF` (Pure White).
- **السبب:** إلغاء أي تحريفات لونية غير معتمدة (مثل `#4f0c16`) وضمان أعلى نسب التباين البصري والوضوح وفق معايير WCAG AAA/AA في الوضعين الفاتح والداكن وواجهات RTL و LTR.

## ADR-010: معمارية ثيمات المتاجر الموحدة (Storefront 4-Theme Presentation Over Unified Inventory)
- **القرار:** اعتماد 4 عائلات تصميم للمتاجر الإلكترونية (Modern Fashion, Kids & Baby, Premium Brand, Wholesale & Uniform) كطبقات عرض وعلامة تجارية (Presentation Layers) فوق نفس المنتجات ومخزون المستأجر وقواعد الحسابات والتكاليف.
- **السبب:** منع تكرار الجداول أو ازدواجية السجلات، وضمان مزامنة المخزون اللحظية مع صالة الإنتاج ومخازن التام دون أي تعارض أو بيع زائد.

## ADR-011: التدقيق البشري الإلزامي لتحويلات InstaPay (Manual InstaPay Verification Policy)
- **القرار:** رفع العميل لإيصال أو مرجع عملية التحويل عبر InstaPay لا يعتبر إثباتاً كافياً للدفع ولا يغير حالة الطلب إلى `verified_paid` أو `shipped` تلقائياً.
- **التنفيذ الصارم:**
  - تحويل حالة الدفع عند الطلب إلى `pending_review`.
  - اشتراط قيام موظف مخول (مدير/محاسب) بمراجعة الحساب البنكي وتسجيل الاعتماد الموثق في `audit_logs` مع تسجيل `verified_by_user_id` ووقت التدقيق.
  - حظر صرف أو شحن أو تسليم أي طلب InstaPay قبل التحقق البشري المعتمد.
  - إتاحة حق الرفض مع بيان السبب الصريح وإشعار العميل.

## ADR-012: تكامل منصة وصلة ورش الصناعية عبر محرك التشغيل للغير (Waslat Worsh Marketplace Architecture)
- **القرار:** بناء منصة "وصلة ورش" كموديول تشغيلي متكامل داخل GarmentOS Cloud وليس كتطبيق مستقل أو متجر موازي.
- **التنفيذ الصارم:**
  - إعادة استخدام محرك التشغيل للغير والقص للغير المعتمد (`SubcontractingService` و `CustomerMaterialReceipt` و `JobOrder`).
  - تحويل عروض أسعار الورش المقبولة مباشرة إلى أوامر تشغيل صناعية (`JobOrder`) مع عزل ملكية خامات العميل وحساب نسب الاستهلاك والتسليم المحاسبي.
  - منع تكرار جداول التشغيل أو إنشاء دفاتر حسابات مزدوجة.

## ADR-013: التوجيه المستقل للمتاجر العامة وتتبع الطلبات (Public Storefront Routing & Order Tracking)
- **القرار:** فصل مسارات المتجر العام وتتبع الطلبات تماماً عن لوحة الـ ERP الخاصة بالمصنع.
- **التنفيذ الصارم:**
  - توفير مسارات مستقلة للعملاء (`#/store/:tenantSlug` و `#/store/track`) والتعرف التلقائي على المستأجر عبر النطاق الفرعي أو النطاق المخصص الموثق.
  - تمكين العميل من تتبع حالة الطلب وتقديم/تحديث إيصال InstaPay باستخدام رقم الطلب ورقم الهاتف فقط دون اشتراط تسجيل دخول في الـ ERP.
  - حماية بيانات المستأجرين الأخرى ومنع أي تسريب لبيانات المصنع أو فواتير العملاء الآخرين.

## ADR-014: محرك أجور القوى العاملة والحصانة التاريخية لمسيرات الرواتب (Phase C: Workforce, Attendance & Payroll Engine)
- **القرار:** توحيد إدارة أجور العمال وحسابات المستحقات ضمن محرك مالي مركزي (`PayrollService`) يدعم نظم التعويض المتعددة (أجر القطعة، أجر ساعي مع أوفرتايم 1.5x، أجر يومي حسب الحضور الفعلي، وراتب شهري ثابت، وهجين).
- **التنفيذ الصارم:**
  - **الحصانة التاريخية (Historical Immutability):** بمجرد إقفال المسير (`finalized`) أو صرف دفعاته (`paid` / `partially_paid`)، يُقفل المسير تماماً ويُمنع أي تعديل أو إعادة احتساب بأثر رجعي لحماية السجلات المالية والمحاسبية.
  - **منع الازدواجية وتكرار الخصم:** ربط كل سجل إنتاجية وسلفة وبدل وخصم جودة بمعرف المسير المسوّى (`settled_payroll_id`) فور احتسابه لمنع حسابه أو خصمه مرتين قط.
  - **دورة الاعتماد الصارمة للخصومات:** حظر الخصم التلقائي لعيوب الجودة؛ لا يُنفذ أي خصم لعيب جودة إلا بعد موافقة صريحة موثقة من مدير الإنتاج، مع تمكين العامل من حق الاعتراض الرسمي.
  - **المدفوعات الجزئية والدفعات المتعددة:** دعم صرف المسيرات عبر دفعات متتالية (`payroll_payments`) مع حظر أي دفعة تتجاوز الرصيد المستحق، وعدم اعتبار المسير مدفوعاً بالكامل (`paid`) إلا عند وصول الرصيد المتبقي إلى الصفر بدقة رقمية.
  - **الشفافية الكاملة (Calculation Breakdown):** تخزين تفاصيل الاحتساب الدقيقة لكل عامل بصيغة JSON داخل بند المسير لتمكين العامل والمحاسب من مراجعة كل مدخل مالي.

## ADR-015: دمج حزم الواجهة الأمامية وتوحيد بناء Vite (Monorepo Frontend Package Consolidation)
- **القرار:** دمج المتاجر العامة ومكتبة المكونات المشتركة داخل تطبيق الويب الرئيسي (`apps/web`) بدلاً من فصلها في حزم متعددة غير متزامنة (`apps/storefront` و `packages/ui`).
- **التنفيذ الصارم:**
  - تنظيم المتجر العام ضمن المسارات المخصصة `#/store/:tenantSlug` و `#/store/track` مع فصل الصلاحيات والبيانات كلياً عن لوحة تحكم الـ ERP.
  - الحفاظ على بناء Vite فائق السرعة وتفادي تعقيدات إدارة الحزم ومشاكل تعارض التبعيات عبر Monorepo.

## ADR-016: معمارية الاشتراكات المرنة ودفتر استهلاك الموارد (Usage-Based SaaS Subscription & Metering Architecture)
- **القرار:** بناء محرك اشتراكات ديناميكي موجه بالبيانات (Data-Driven Entitlements & Metering Engine) يتيح لمدير المنصة ضبط الباقات والأسعار والكوتا والمحددات عبر الواجهة بدون تغيير الكود.
- **التنفيذ الصارم:**
  - توثيق كافة حركات الاستهلاك ضمن دفتر قيود استهلاك غير قابل للتعديل (`subscription_usage_events`) باستخدام مفاتيح Idempotency لمنع التكرار أو التلاعب.
  - تطبيق قيود الكوتا الصارمة (Hard Limits) على العمليات الإنشاء الأساسية، مع منح حصانة للعمليات التشغيلية والمالية الجارية (Cutting Lays & Payroll Runs) لضمان عدم توقف خطوط الإنتاج.
  - دعم طلبات الترقية الذاتية ومهل السداد (Grace Periods) والاستثناءات الإدارية المؤقتة.

## ADR-017: حصر نطاق الحضور والانصراف في التطبيق واستبعاد أجهزة البصمة المباشرة (Application Attendance vs Biometric Hardware Exclusion)
- **القرار:** استبعاد التكامل المادي المباشر وبروتوكولات أجهزة الحضور بالبصمة (Biometric Hardware Direct Integration) من نطاق النظام السحابي، والاعتماد التام على سجلات الحضور والانصراف الموثقة عبر واجهات التطبيق ومسارات الـ REST API المعتمدة.
- **السبب:** تباين بروتوكولات أجهزة الحضور المحلية (ZKTeco، أنظمة التحكم بالأبواب) واعتمادها على شبكات داخلية معقدة؛ تركيز المنصة السحابية على محرك الرواتب والإنتاجية وأجور القطعة.

## ADR-018: معمارية منصة وصلة ورش الصناعية المتكاملة (Waslat Worsh Integrated Marketplace Architecture)
- **القرار:** بناء منصة "وصلة ورش" كموديول سوق صناعي متكامل داخل المنصة يربط المصانع التي تبحث عن طاقات تشغيل مع الورش المتخصصة (قص، خياطة، تطريز، طباعة).
- **التنفيذ الصارم:**
  - دورة متكاملة: نشر طلب عروض أسعار (RFQ) ← تلقي عروض الورش المعتمدة ← الترسية والموافقة ← التحويل المباشر لأمر تشغيل صناعي (`JobOrder`) عبر `SubcontractingService`.
  - احتساب عمولات المنصة وتسجيلها في دفتر الحسابات تلقائياً مع توثيق تقييمات الجودة والالتزام بالمواعيد.

## ADR-019: معالجة استثناءات المصادقة وتقييد معدل طلبات الـ API (Unified API 401 Exception Contract & Tiered Rate Limiting)
- **القرار:** 
  1. حظر إعادة توجيه عملاء الـ API إلى مسارات ويب غير معرفة (`route('login')`) عند غياب التوكن.
  2. إلزام كافة مسارات الـ `api/*` بإرجاع استجابة JSON موحدة برمز HTTP 401 دون تسريب تتبع المكدس (Stack Trace).
  3. تطبيق تقييد معدل الطلبات حسب مستوى الخطورة (Rate Limiting by Endpoint Risk):
     - المصادقة وتخمين كلمات المرور: 10 طلبات/دقيقة بالـ IP.
     - المتجر الإلكتروني وتتبع الطلبات: 60 طلباً/دقيقة.
     - استكشاف دليل الورش: 60 طلباً/دقيقة.
     - طرح عروض الأسعار والـ RFQ: 15 طلباً/دقيقة لكل مستخدم.
     - إشعارات الدفع والـ Webhooks: 60 طلباً/دقيقة لكل IP.
     - تصدير التقارير المالية الثقيلة: 15 طلباً/دقيقة لمنع استنزاف خوادم الإنتاج.
  4. تفعيل صلاحية توكنات Sanctum الافتراضية بـ 7 أيام (`10080` دقيقة) قابلة للتهيئة عبر `.env` لمنع بقاء الرموز المسربة صالحة للأبد.

## ADR-020: تجزئة حزم الفرونت إند والتحميل الكسول للوحدات ومنع وميض الاتجاه (Route/Tab-Level Lazy Loading & DIR Flash Prevention)
- **القرار:**
  1. تقسيم حزمة التطبيق الرئيسية عبر `React.lazy()` و `Suspense` على مستوى التبويبات والوحدات المستقلة (`WarehouseManagerTab`, `SubcontractingTab`, `AccountingTab`, `HrTab`, `SalesTab`, `WaslatWorshTab`, `TenantSubscriptionView`, `PlatformAdminDashboard`, `PublicStorefrontView`).
  2. تخفيض حجم حزمة الـ JavaScript الأولية المحملة من `1,341.89 kB` إلى `764.11 kB` (تقليص بنسبة 43.1%).
  3. تضمين سكريبت فوري في رأس صفحة `index.html` لتحديد اتجاه المستند ولغته (`dir="rtl"` و `lang="ar"`) قبل بدء تحميل وتصيير React لمنع الوميض البصري (DIR Flash) لمستخدمي اللغة العربية مع الحفاظ على خيار اللغة الإنجليزية.
